## User Scenarios & Testing

### User Story 1 - 清楚回應贈予選擇 (Priority: P1)

玩家在對手執行贈予後，需要從對手提供的三張物品牌中選擇一張。畫面應讓玩家快速看懂自己正在回應贈予、目前可選的卡片有哪些、每張卡片的圖像與魅力值，以及點擊後會送出哪一張。

**Why this priority**: 贈予是玩家直接回應對手行動的高頻互動；若畫面仍像一般卡片清單，玩家容易看不出目前任務與可選範圍。

**Independent Test**: 進入 NPC 或多人對戰並觸發贈予回應，確認玩家能在不閱讀額外說明的情況下辨識三張可選卡、選中其中一張，且既有贈予解析流程照常完成。

**Acceptance Scenarios**:

1. **Given** 對手提供三張贈予卡片，**When** 玩家看到回應畫面，**Then** 畫面以同一個清楚的贈予選擇表面呈現三張卡，且每張卡都有可辨識圖像、魅力值與可點擊範圍。
2. **Given** 玩家準備選擇贈予卡片，**When** 玩家點擊其中一張，**Then** 系統立即送出該張卡作為贈予回應，並維持既有遊戲流程與結果呈現。
3. **Given** 玩家在手機寬度操作，**When** 贈予回應畫面開啟，**Then** 三張卡與主要操作區不應超出主要畫面寬度；選項可在表面內部垂直堆疊或換行，以保留卡面可讀性與必要互動入口。

---

### User Story 2 - 清楚建立競爭分組 (Priority: P1)

玩家執行競爭時，需要從四張已選手牌中選擇一種二對二分組方式。畫面應將三種分組方案清楚呈現，讓玩家能比較每一組的卡片內容、單卡魅力值與每組魅力合計，並明確知道「使用此分組」會提交哪一種方案。

**Why this priority**: 競爭分組是玩家主動送出前的關鍵決策；若方案比較不清楚，玩家容易誤送分組並影響局勢。

**Independent Test**: 玩家選取四張手牌並執行競爭，確認三種分組方案可被清楚比較，選擇任一方案後既有競爭送出流程照常完成。

**Acceptance Scenarios**:

1. **Given** 玩家已選擇四張手牌並啟動競爭，**When** 分組畫面開啟，**Then** 系統呈現三種可用分組方案，每個方案都清楚分成兩組。
2. **Given** 分組畫面顯示，**When** 玩家比較不同方案，**Then** 每張卡的圖像與單卡魅力值仍可辨識，每組顯示魅力合計，且同一方案內的兩組不會混淆。
3. **Given** 玩家選擇某一分組方案，**When** 玩家點擊該方案的送出操作，**Then** 系統立即使用該方案進行既有競爭流程，不改變競爭規則或分組合法性。

---

### User Story 3 - 清楚回應競爭選組 (Priority: P2)

玩家在對手執行競爭後，需要從對手提供的兩組卡片中選擇一組。畫面應清楚區分兩組卡片，讓玩家能理解每一組包含哪些卡、單卡魅力值與每組魅力合計，再送出選擇。

**Why this priority**: 回應競爭雖然依賴既有規則，但畫面若無法清楚區分兩組，玩家容易選錯組。

**Independent Test**: 觸發對手競爭回應，確認玩家能清楚比較兩組卡片並選擇其中一組，且結果仍由既有流程解析。

**Acceptance Scenarios**:

1. **Given** 對手提供兩組競爭卡片，**When** 玩家看到回應畫面，**Then** 兩組卡片以清楚分隔的選項呈現。
2. **Given** 玩家比較兩組卡片，**When** 玩家查看任一組，**Then** 該組內每張卡的圖像與單卡魅力值可辨識，每組顯示魅力合計，且不會與另一組混在一起。
3. **Given** 玩家選擇其中一組，**When** 玩家點擊該組，**Then** 系統立即送出選擇並維持既有競爭解析流程，不改變分數、卡片歸屬或回合狀態規則。

---

### User Story 4 - 與 Ginza 視覺與手機操作一致 (Priority: P3)

玩家在贈予與競爭相關畫面中，應感受到與 Ginza v2 房間、人物卡 coverflow、扇形手牌一致的視覺語言。手機上仍應能穩定操作，不需要額外學習新的互動模式。

**Why this priority**: 006-008 已更新主要遊戲表面；贈予與競爭若維持舊式樣式，會造成視覺割裂與手機操作不一致。

**Independent Test**: 在桌機與手機寬度分別檢查贈予回應、競爭分組、競爭回應畫面，確認風格一致、主要操作清楚、沒有主要內容水平捲動。

**Acceptance Scenarios**:

1. **Given** 任一贈予或競爭表面開啟，**When** 玩家查看畫面，**Then** 表面風格應與目前遊戲房間背景、人物卡與手牌視覺相容。
2. **Given** 玩家在手機寬度操作，**When** 贈予或競爭表面開啟，**Then** 玩家可完成必要點擊，主要內容不得出現水平捲動；表面內部可垂直堆疊或換行以保留卡面可讀性。
3. **Given** 結果提示或行動動畫存在，**When** 贈予或競爭表面顯示，**Then** 既有提示與動畫仍可辨識，且不得遮蔽必要選項。

## Requirements

### Functional Requirements

- **FR-001**: 系統 MUST 將贈予回應畫面整理為清楚的選擇表面，呈現三張可選卡片與每張卡的主要資訊。
- **FR-002**: 系統 MUST 讓玩家能直接從贈予回應畫面選擇一張卡，並維持既有贈予解析流程。
- **FR-003**: 系統 MUST 將競爭分組畫面整理為清楚的方案比較表面，呈現三種二對二分組方案。
- **FR-004**: 系統 MUST 在競爭分組畫面中清楚區分每個方案內的兩組卡片，並為每組顯示該組魅力合計，避免玩家誤解分組內容。
- **FR-005**: 系統 MUST 讓玩家能從競爭分組畫面選擇一種方案，並維持既有競爭送出流程。
- **FR-006**: 系統 MUST 將競爭回應畫面整理為清楚的兩組選擇表面，讓玩家能比較每組單卡資訊與魅力合計並選擇其中一組。
- **FR-007**: 系統 MUST 保留每張卡片的卡面圖像與魅力值顯示，且在桌機與手機寬度都不得讓主要資訊完全不可辨識。
- **FR-008**: 系統 MUST 保留既有贈予與競爭的卡片張數、可選方案、選擇結果、回合流程與勝負判定。
- **FR-009**: 系統 MUST 保留既有等待對手、回應互動、結果提示與行動動畫的可辨識性。
- **FR-010**: 系統 MUST 在手機寬度維持贈予與競爭相關表面的可操作性，主要內容不得造成水平捲動。
- **FR-011**: 系統 MUST NOT 顯示任何對手手牌、秘密牌或尚未公開的選擇資訊。
- **FR-012**: 系統 MUST NOT 修改卡牌資料、角色資料、行動 payload、Socket.IO event、shared type 契約、計分、回合或勝負規則。
- **FR-013**: 系統 MUST 保留贈予與競爭相關畫面的既有 bottom sheet 互動模型，僅調整 bottom sheet 內部的卡片、分組與選項呈現。
- **FR-014**: 系統 MUST 保留贈予選卡、競爭分組送出與競爭選組的點擊即送出行為，不新增點擊前選中預覽或二次確認流程。
- **FR-015**: 系統 MUST 為贈予與競爭的可點擊選項提供清楚的 hover、press 與 keyboard focus 視覺回饋。
- **FR-016**: 系統 MUST 在手機寬度允許贈予與競爭選項於 bottom sheet 內部垂直堆疊或換行，優先保留卡面可讀性與操作可點擊性。

### Non-Functional Requirements

- **NFR-001**: 贈予與競爭相關表面 MUST 與 Ginza v2 房間背景、007 人物卡 coverflow、008 扇形手牌的視覺語言相容。
- **NFR-002**: 玩家 SHOULD 能在畫面開啟後 5 秒內理解目前要做的是贈予選卡、競爭分組或競爭選組。
- **NFR-003**: 玩家 SHOULD 能在桌機與手機寬度於 3 秒內辨識每個可選項的卡片內容、競爭組別魅力合計與主要操作按鈕。
- **NFR-004**: 互動表面的開啟、選項點擊與結果提示 SHOULD 在 200ms 內提供主要視覺回饋，且不得造成明顯操作卡頓。

### Key Entities

- **贈予回應表面**: 對手執行贈予後，玩家從三張卡中選一張的互動畫面。
- **競爭分組表面**: 玩家執行競爭時，從四張已選手牌產生並選擇三種二對二方案的互動畫面。
- **競爭回應表面**: 對手執行競爭後，玩家從兩組卡片中選擇一組的互動畫面。
- **互動卡片選項**: 贈予或競爭表面中的單張或一組卡片，包含卡面圖像、單卡魅力值、競爭組別魅力合計與可操作狀態。

## Success Criteria

- **SC-001**: 在贈予回應畫面中，玩家能於 5 秒內辨識三張可選卡片並完成一張選擇。
- **SC-002**: 在競爭分組畫面中，玩家能於 10 秒內辨識三種分組方案、各組魅力合計並選擇其中一種。
- **SC-003**: 在競爭回應畫面中，玩家能於 5 秒內辨識兩組卡片、各組魅力合計並完成一組選擇。
- **SC-004**: 桌機與手機寬度下，贈予與競爭表面主要內容不出現水平捲動；手機寬度可透過內部垂直堆疊或換行保持卡面可讀與主要操作可點擊。
- **SC-005**: 贈予與競爭的既有結果、卡片歸屬、行動消耗、回合流程、計分與勝負判定維持不變。
- **SC-006**: 實作後通過標準前端測試與建置驗證，並完成贈予回應、競爭分組、競爭回應三個畫面的手動操作檢查。

## Assumptions

- 009 是贈予與競爭相關互動畫面的 UI polish，不改遊戲規則。
- 贈予與競爭相關表面延續既有 bottom sheet 架構，不改成新的置中 modal 或新互動容器。
- 贈予與競爭相關表面延續既有點擊即送出流程，不新增中間選中狀態。
- 手機寬度優先保留卡面可讀性，可接受 bottom sheet 內部垂直捲動，但不得造成主要頁面水平捲動。
- 贈予仍固定由對手提供三張、回應者選一張。
- 競爭仍固定使用四張卡形成三種二對二方案，回應者從兩組中選一組。
- 詳細視覺驗收由使用者手動確認；自動驗證聚焦於既有測試與建置。

## Out of Scope

- 修改贈予或競爭的規則、卡片張數、分組生成邏輯、計分、勝負判定或 server validation。
- 新增、刪除或修改 action payload、Socket.IO event names 或 shared type 契約。
- 修改卡牌資料、角色資料、物品牌組或圖片來源。
- 將贈予或競爭表面改成新的置中 modal、全螢幕流程或其他非 bottom sheet 架構。
- 新增贈予或競爭選項的二次確認、暫存選中預覽或額外送出步驟。
- 重做主手牌扇形、人物卡 coverflow、房間背景、行動 token 或回合結算表面。
- 新增教學流程、AI 建議、策略提示或自動推薦選項。
- 版本號調整、CHANGELOG 更新或 release 準備。
