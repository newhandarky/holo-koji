- Q: 手機版扇形手牌要怎麼處理卡片重疊密度？ → A: 手機維持扇形並提高重疊密度，焦點卡抬起放大。

- Q: 桌機版扇形手牌要呈現到什麼展開程度？ → A: 中等展開，保留扇形重疊但每張仍有明確點擊區。

## User Scenarios & Testing

### User Story 1 - 以扇形手牌檢視自己的卡片 (Priority: P1)

玩家在 active game room 中查看自己的手牌時，手牌不再以平鋪小方塊呈現，而是以扇形排列顯示。玩家能在不展開額外視窗的情況下辨識每張手牌的圖像、魅力值與目前是否被選取。

**Why this priority**: 扇形手牌是本功能的核心改版；若主手牌仍維持現有平鋪排列，後續點擊放大與手機操作都無法正確驗收。

**Independent Test**: 進入 active game room 並查看自己的手牌，確認手牌呈扇形排列，所有手牌都可辨識、可點選，且選取狀態仍清楚。

**Acceptance Scenarios**:

1. **Given** 玩家進入 active game room 且手上有卡，**When** 主手牌區顯示，**Then** 系統以扇形排列呈現玩家自己的手牌；桌機寬度使用中等展開，保留扇形重疊但每張仍有明確點擊區。
2. **Given** 手牌以扇形呈現，**When** 玩家查看任一卡片，**Then** 玩家仍能辨識卡面圖像與魅力值。
3. **Given** 玩家點選一張手牌，**When** 該卡被選取或取消選取，**Then** 該卡同時成為放大焦點，選取狀態仍清楚顯示，且不改變既有選牌規則。
4. **Given** 玩家在手機寬度查看手牌，**When** 扇形手牌顯示，**Then** 系統應維持扇形排列並允許較高重疊密度，主要手牌區不得造成水平捲動或遮住主要操作按鈕。

---

### User Story 2 - 點擊手牌時局部放大 (Priority: P2)

玩家點擊手牌時，被點擊的原卡片會在扇形手牌中抬起並放大，讓玩家能更容易確認卡面內容；放大效果不得替代既有選牌流程，也不得打開新的互動視窗或額外產生預覽卡。

**Why this priority**: 扇形排列會讓卡片互相重疊，局部放大能降低誤選與辨識成本，但必須保持既有行動流程穩定。

**Independent Test**: 點擊任一手牌，確認原卡片在扇形中抬起並放大且選牌狀態同步更新；再次點擊或選其他牌時，放大焦點能正確切換或收回。

**Acceptance Scenarios**:

1. **Given** 玩家有多張手牌，**When** 玩家點擊其中一張，**Then** 原本被點擊的卡片應在扇形手牌中抬起並局部放大。
2. **Given** 一張手牌已放大，**When** 玩家點擊另一張手牌，**Then** 放大焦點應切換到新點擊的卡片。
3. **Given** 玩家選擇行動所需張數，**When** 卡片因點擊被選取並成為放大焦點，**Then** 既有行動按鈕啟用條件與提示不得改變。
4. **Given** 互動視窗或 bottom sheet 開啟，**When** 玩家查看或選擇卡片，**Then** 既有互動視窗內容與操作不應被主手牌放大效果干擾。

---

### User Story 3 - 維持既有手牌流程與手機可玩性 (Priority: P3)

玩家在抽牌、選牌、使用四種行動、等待對手互動與回合切換時，手牌扇形視覺不應造成流程變更或資訊誤導。手機上仍應能穩定點擊卡片與主要操作按鈕。

**Why this priority**: 手牌是所有行動的入口；視覺改版若破壞操作流程，會直接影響遊戲可玩性。

**Independent Test**: 在 NPC 或多人房間中執行基本手牌選取與至少一種行動流程，確認扇形手牌不改變行動規則、選牌數量、抽牌動畫與回合流程。

**Acceptance Scenarios**:

1. **Given** 回合開始並抽到新卡，**When** 新卡加入手牌，**Then** 手牌扇形應更新且新卡提示仍可辨識。
2. **Given** 玩家選擇密約、取捨、贈予或競爭行動所需卡片，**When** 已選卡片數量符合規則，**Then** 既有行動流程可照常進行。
3. **Given** 玩家等待對手操作或互動視窗開啟，**When** 主手牌區存在，**Then** 手牌視覺不得洩漏對手手牌、秘密牌或未公開選擇。
4. **Given** 玩家在手機寬度操作，**When** 點擊、取消選取或切換放大卡片，**Then** 手勢與點擊不應與 bottom sheet 或頁面捲動產生明顯衝突。

## Requirements

### Functional Requirements

- **FR-001**: 系統 MUST 在 active game room 的我方主手牌區以扇形排列顯示玩家自己的手牌。
- **FR-001a**: 桌機寬度的扇形手牌 MUST 使用中等展開，保留卡片重疊感，同時讓每張手牌仍有明確可點擊區域。
- **FR-002**: 系統 MUST 保留每張手牌的卡面圖像與魅力值顯示，且扇形重疊不得讓主要資訊完全不可辨識。
- **FR-003**: 系統 MUST 讓玩家可直接點擊扇形手牌中的任一卡片進行既有選取或取消選取，且被點擊的卡片 MUST 同時成為放大焦點。
- **FR-004**: 系統 MUST 在手牌被選取時提供清楚的選取狀態，不得只依賴難以辨識的細微變化。
- **FR-005**: 系統 MUST 在玩家點擊手牌時，讓原本被點擊的卡片在扇形手牌中抬起並局部放大，不得額外產生預覽卡。
- **FR-006**: 系統 MUST 讓局部放大焦點可在不同手牌間切換；焦點 MUST 跟隨最後一次被點擊選取或取消選取的手牌，並在手牌變更或選取流程重置時回到一致狀態。
- **FR-007**: 系統 MUST 保留既有四種行動的選牌數量、啟用條件、提示與送出流程。
- **FR-008**: 系統 MUST 保留抽牌後新卡提示與既有手牌更新行為。
- **FR-009**: 系統 MUST 在手機寬度維持主手牌區可操作，且不得造成頁面主要區域水平捲動。
- **FR-009a**: 手機寬度的扇形手牌 MUST 維持扇形排列並允許較高重疊密度，且被點擊或選取的焦點卡 MUST 能抬起放大。
- **FR-010**: 系統 MUST 保留 bottom sheet、贈予互動視窗、競爭互動視窗與順序決定視窗的既有操作可用性。
- **FR-011**: 系統 MUST NOT 顯示任何對手手牌、秘密牌或尚未公開的選擇資訊。
- **FR-012**: 系統 MUST NOT 修改卡牌資料、行動 payload、Socket.IO event、回合流程、計分或勝負判定。

### Non-Functional Requirements

- **NFR-001**: 扇形手牌 MUST 在桌機與手機寬度都保持可讀、可點擊、主要操作不被遮擋；桌機寬度使用中等展開，手機寬度可透過提高卡片重疊密度維持扇形。
- **NFR-002**: 手牌點擊與局部放大 SHOULD 讓玩家在 1 秒內感知目前焦點卡與選取狀態。
- **NFR-003**: 手牌視覺改版 MUST 與 Ginza v2 房間背景、007 人物卡 coverflow 與既有 bottom-sheet 操作風格相容。
- **NFR-004**: 手牌重新排列與放大效果 SHOULD 在互動後 200ms 內完成主要視覺回饋（至少可辨識焦點切換或選取狀態改變），且不得出現連續可見掉幀造成的明顯操作卡頓。

### Key Entities

- **玩家手牌**: 玩家目前可用於行動選擇的手牌集合，包含卡面圖像、魅力值與選取狀態。
- **扇形手牌區**: active game room 中呈現玩家手牌的主視覺區域，以弧形、角度或重疊方式排列卡片。
- **局部放大卡片**: 玩家點擊後在原扇形位置抬起並放大的單張手牌，用於提高辨識度，但不代表新的遊戲狀態。
- **選取狀態**: 玩家已選取用於行動的手牌狀態，必須延續既有選牌流程；玩家點擊手牌時，選取狀態與放大焦點同步更新。

## Success Criteria

- **SC-001**: 玩家在 active game room 中能於 5 秒內辨識主手牌區已改為扇形排列，且可看出目前手牌張數；桌機寬度能看出中等展開與明確點擊區。
- **SC-002**: 玩家可在桌機與手機寬度點選任一手牌，並在 1 秒內看出該卡已同步切換選取狀態且成為目前放大焦點。
- **SC-003**: 玩家在手機寬度操作手牌時，手牌仍呈扇形且焦點卡可抬起放大，主畫面不得出現主要內容水平捲動，且主要行動按鈕與 bottom sheet 入口仍可操作。
- **SC-004**: 密約、取捨、贈予、競爭四種行動的選牌張數與可送出條件維持既有行為。
- **SC-005**: 抽牌提示、手牌更新與等待對手狀態下，扇形手牌不洩漏任何隱藏資訊。
- **SC-006**: 實作後通過標準前端測試與建置驗證，並完成桌機與手機寬度的手動操作檢查。

## Assumptions

- 008 只調整 active game room 中玩家自己的主手牌區，不調整互動視窗內的卡片排列。
- 手牌局部放大是視覺輔助，不新增遊戲狀態，也不取代既有選牌狀態。
- 手牌張數以現有遊戲流程為準；本 spec 不改抽牌、出牌、棄牌或手牌上限規則。
- 007 人物卡 coverflow 與 006 Ginza 房間主題已存在，008 需與其共存。

## Out of Scope

- 修改卡牌資料、角色資料、物品牌組或圖片來源。
- 修改四種行動規則、選牌張數、計分、勝負判定或 server validation。
- 新增、刪除或修改 action payload、Socket.IO event names 或 shared type 契約。
- 重做贈予互動視窗、競爭互動視窗、順序決定視窗或 bottom sheet 架構。
- 修改人物卡 coverflow、角色卡面、場上位置或掌控邊框。
- 版本號調整、CHANGELOG 更新或 release 準備。
